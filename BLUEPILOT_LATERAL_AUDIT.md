# BluePilot Ford Angle-Control Audit

**Source:** `BluePilotDev/bluepilot`, branch `bp-dev` (its default/HEAD branch), commit `501a7c0e911245044196fcc90cb077a69fa0749b`. Note the repo also carries versioned branches (`bp-1.1` … `bp-7.0`), plus experimental branches including `bp-no-stall` and `bp-dev-f150-mk14.5` that we did not check out — `bp-dev` is BluePilot's active development head and is what this audit reflects. BluePilot is itself a fork of **sunnypilot**, and vendors a full copy of `opendbc` at `opendbc_repo/` (not a git submodule — committed directly) plus a thin `panda` fork (`sunnyhaibin/panda`).

**Architecture BluePilot uses:** rather than editing `opendbc/car/ford/*.py` heavily in place, BluePilot keeps those files close to upstream and layers almost all Ford-specific logic in a parallel tree, `opendbc/sunnypilot/car/ford/*_ext.py`, with small, explicit call-outs from the base files. This "extension" pattern is directly relevant to `FLASHPILOT_ARCHITECTURE.md` — it's a proven way to keep a fork's diff against upstream small and reviewable.

**Important terminology correction up front:** upstream Ford lateral control is already `steerControlType = angle` (see `FLASHLIGHTNING_UPSTREAM_AUDIT.md` §7) — openpilot already sends a closed-loop curvature/angle command, not a torque. BluePilot's "angle control" is specifically about which **DBC signal** is the primary actuator on the `LateralMotionControl2` message:

- **Curvature-primary** (`LatCtlCurv_No_Actl`, signal `c2`) — what upstream sends today, the only signal upstream ever sets nonzero.
- **Path-angle-primary** (`LatCtlPath_An_Actl`, signal `c1`) — BluePilot's newer, selectable alternative, implemented in `opendbc/sunnypilot/car/ford/lateral_angle_ext.py`.

Both live behind BluePilot's `opendbc/sunnypilot/car/ford/lateral_curv_ext.py` (curvature-primary, the older/proven "4-signal" strategy) and `lateral_angle_ext.py` (angle-primary, newer). FlashPilot's stated goal is the **angle-primary** path, so that file is the primary audit subject; `lateral_curv_ext.py` is noted only where angle mode depends on it.

## Component classification

| # | Component | File(s) | Classification | Notes |
|---|---|---|---|---|
| 1 | κ→path_angle core calculation (`path_angle = ½·κ·d_ref`) | `lateral_angle_ext.py:131-137, 474-519` | **REQUIRED** | The actual angle-control algorithm. `d_ref` is a speed-indexed lookup table (`_PSCM_DREF_SPEEDS_MS/_M`) approximating the PSCM's internal lookahead distance — BluePilot states this is reverse-engineered (references an internal "PSCM knowledge pack" doc we don't have). **Treat the geometry relation itself as sound (standard small-angle path geometry) but treat the specific `d_ref` table as an empirical constant needing re-validation, not a given.** |
| 2 | Model-predicted curvature blend (`predicted_curvature`, `path_angle_blend_ratio`, "exit-biased" blend) | `lateral_angle_ext.py:396-471` | **REQUIRED for parity, but HIGH-COMPLEXITY / HIGH-TUNING-RISK** | Uses `modelV2.orientationRate.z` to look further ahead than the planner alone, blended in to reduce lag; the exit-biased logic exists specifically to stop this blend from causing overshoot exiting a curve. This is the single most tuned, most road-tested part of the file (references specific route IDs, dated comments about specific failure modes). Recommend porting the mechanism but re-tuning breakpoints/ratios against F-150 Lightning road data rather than trusting the numbers as-is (they were tuned on Mach-E / mixed fleet data — see items 5, 8). |
| 3 | Variable Lookup Time (VLT) | `lateral_angle_ext.py:79-90, 396-416` | **OPTIONAL for a first cut** | Adapts how far ahead the blend looks based on speed and curvature magnitude. Meaningfully improves curve-entry smoothness per BluePilot's comments, but is a tuning refinement layered on top of item 2, not required for path_angle control to function at all. Can be deferred (fixed lookup time) for the first "boring" version. |
| 4 | PSCM authority-limit clamp (`_pscm_lim`, `_in_hard_sat`, `_dbc_sat`) | `lateral_angle_ext.py:434-541` | **REQUIRED** | Handles the PSCM's own internal steering-authority ceiling (observed hardware behavior: the PSCM stops honoring further magnitude increases and can lag badly on release if not respected). This is the "steering saturation" item from the task list. Directly addresses real hardware behavior, not speculative. |
| 5 | Soft rate-of-change (ROC) limiter | `lateral_angle_ext.py:543-558` | **REQUIRED** | Python-side speed-indexed `path_angle` rate cap, tighter than panda's C-side limit (panda mirrors it at ×1.02 looser — see `FLASHPILOT_SAFETY_AUDIT.md`). Comments explicitly document a **cadence bug already found and fixed once** (constants authored at a since-abandoned 100 Hz control cadence, rescaled ×5 for the shipped 20 Hz cadence) — a good example of exactly the class of bug FlashPilot should watch for if we ever change `CarControllerParams.STEER_STEP`. |
| 6 | Ford CAN messages used | `LateralMotionControl2` (`path_angle`/`c1` field, already exists upstream, just left at 0); `Lane_Assist_Data1` (repurposed, see item 7) | **REQUIRED (no new CAN IDs)** | Angle mode does **not** introduce any new CAN identifier. It uses fields already defined in the DBC on a message upstream already transmits every cycle. This substantially lowers the integration risk versus "add a new message." |
| 7 | `angle_mode_engaged` + `shadow_curvature` signaling | `lateral_angle_ext.py:170-176, 572-581`; `fordcan_ext.py:23-60` | **REQUIRED** | Packs 3 bytes of state into previously-always-zero bits of `Lane_Assist_Data1` (byte 4 bit 0, bytes 5-6) so panda's C safety code can know angle mode is live and cross-check the path_angle command against the vehicle's actual curvature, without a new CAN ID or an RX round trip (BluePilot's own comment: they tried a dedicated message first and found panda cannot self-receive its own TX). This is the mechanism that lets panda apply *any* deviation check to `path_angle`, since the real `curvature` field is pinned at 0 in angle mode (see `FLASHPILOT_SAFETY_AUDIT.md` for the safety-side half of this). |
| 8 | Speed-factor / per-platform gain calibration | `lateral_angle_ext.py:47-64, 196-207` | **REQUIRED, but explicitly UNVALIDATED for our truck** | Three hardcoded gain presets (`_GAIN_CAN`, `_GAIN_CANFD_BOF`, `_GAIN_CANFD_SUV`). The Lightning is grouped under `_CANFD_BOF_CARS` ("CAN-FD body-on-frame trucks": F-150 MK14, Lightning, Expedition, Ranger) — i.e. BluePilot already has a *category* tune that includes the Lightning, but not a Lightning-specific one, and the Lightning is a heavier EV with a different weight distribution than its ICE siblings. Use as a documented starting point, not a validated constant. |
| 9 | Human steering-override logic | `human_turn.py` (all), used from `lateral_angle_ext.py:301-343` | **REQUIRED** | Shared `HumanTurnDetector` class (also used by curvature-primary mode). Latches "human turn" on sustained `steeringPressed` + `|steeringAngleDeg| > 45°` for 1.5 s (3.0 s if the wheel was already past 45° when contact began, to distinguish an intentional takeover from a mid-curve nudge — validated against a specific dated road-test route in the comments). On latch, angle mode forces **mode 0** (fully inactive on the wire) rather than letting `path_angle` wind up to a stale value — documented as avoiding a specific 2-3s PSCM re-engage stall observed on a Mach-E. Mode 0 is safety-neutral by construction (every panda check has a `!steer_control_enabled` branch). |
| 10 | Stall detection/recovery ("post-override stall blip") | `lateral_angle_ext.py:105-129, 345-389, 591-612` | **REQUIRED-IF-REPRODUCIBLE, NEEDS TRUCK VALIDATION** | A *second*, more novel mechanism, separate from item 9: after certain driver-touch episodes, BluePilot observed the PSCM keeps reporting "InProgress" but silently attenuates path_angle delivery to ~0.56× for several seconds — a stall the driver reads as "not engaging." The fix is a deliberate ~300 ms drop to mode 0 ("blip") to force the PSCM to reset its internal authority state, both reactively (when the deviation-clip has been binding for ≥0.5 s) and proactively (on release of any sustained driver press). This is empirically discovered and tuned on specific dated road-test routes referencing a Mach-E's PSCM — **we have no evidence this reproduces on the Lightning's PSCM, or with the same timing**. Recommend porting the mechanism (it's cheap and mode-0-safe) but treating the thresholds as needing our own truck's validation, and being prepared for it to simply never fire if our PSCM doesn't exhibit the behavior. |
| 11 | "Anti-weave" logic | *(no dedicated module)* | **REQUIRED, as an emergent property — not a separate port** | No component is named "anti-weave." The oscillation-damping behavior the task is asking about is the *combination* of items 4 (saturation clamp), 5 (soft ROC), 2's exit-biased blend (prevents the model from re-introducing curvature right as the planner is unwinding), and 9/10 (clean hand-back instead of a stale wound-up command). There is nothing further to extract as a standalone piece. |
| 12 | Lane centering trim ("advanced lane positioning") | `lane_center_trim.py` (all) | **NOT NEEDED (phase 0)** | A curvature-domain nudge toward true lane-line center + user L/R bias, applied to `kappa_cmd` before all the above limiters. Explicitly a UX/preference feature, not required for path_angle control to work — and its own docstring documents a *failed* earlier attempt to do this as an additive trim directly on `path_angle` (wrong speed-dependence, bypassed limiters), which is itself a useful cautionary note: **do not add any lateral-position trim as a raw additive delta on `path_angle`.** |
| 13 | Pinion-angle curvature measurement (`STEER_ANGLE_CURVATURE`) | `values_ext.py:44-101`; consumed in `ford.h` | **NOT NEEDED (phase 0)** | An alternate `angle_meas` source (steering-pinion angle via `SteeringPinion_Data`/0x7E, converted through a per-platform slip-factor/steer-ratio/wheelbase table — the Lightning already has a row here, index 7) for vehicles whose yaw sensor is implausible. This is a workaround for a *different* problem (bad yaw sensor) than path-angle-primary control, is independently toggleable, and pulls in an entire separate ABI mechanism (item 14) we don't otherwise need. |
| 14 | `current_safety_param_sp` / "SP safety param" plumbing | `values_ext.py:45-53`; consumed in `ford.h` | **NOT NEEDED (phase 0)** | A sunnypilot-wide extra USB control transfer that delivers a second `uint16` safety param ahead of the main one. **We confirmed this does not exist in upstream `commaai/opendbc`'s safety headers at all** — it's a sunnypilot-family-only ABI extension. Adopting item 13 would require adopting this too. Since item 13 itself is out of scope, so is this. This is the single biggest "don't pull this thread" boundary in the whole audit. |
| 15 | Panda safety changes for `path_angle`/value-range/ROC checks | `opendbc/safety/modes/ford.h` (BluePilot diff) | **REQUIRED (subset)** | Covered in full in `FLASHPILOT_SAFETY_AUDIT.md`. ## Dependency chain for a minimal angle-primary port

Reading `lateral_angle_ext.py` top to bottom, the **irreducible** dependency chain for FlashPilot's Lightning-only, no-lane-trim, no-pinion, fixed-lookup-time version is:

```
CarControllerParams (STEER_STEP=5, CURVATURE_ERROR)      [upstream, unchanged]
        │
        ▼
HumanTurnDetector (human_turn.py)                          [port as-is, REQUIRED]
        │
        ▼
new FlashPilot angle-control module (BluePilot's           [new, minimal subset of
  lateral_angle_ext.py, trimmed: no lane_center_trim,        lateral_angle_ext.py —
  no pinion, no VLT, no user Params surface, fixed             see FLASHPILOT_ARCHITECTURE.md]
  path_angle_blend_ratio constant)
        │
        ▼
fordcan.create_lat_ctl2_msg (+ ramp_type/precision_type     [small upstream extension,
  params) and create_lka_msg (+ angle_mode_engaged/           REQUIRED]
  shadow_curvature packing)
        │
        ▼
opendbc/safety/modes/ford.h: FORD_PATH_ANGLE_LIMITS,        [REQUIRED safety change —
  path_angle_cmd_checks, angle_mode_engaged/shadow_             see FLASHPILOT_SAFETY_AUDIT.md]
  curvature latch, ford_shadow_curvature_error_check
```

No panda `current_safety_param_sp` channel, no pinion geometry table, no lane-centering trim, and no ICBM/BP-Long/MADS code are on this critical path.
